# Interview Questions: AWS Three-Tier Web Application

20 interview questions an interviewer could ask about this exact project, with detailed model answers.

---

## 1. Walk me through the architecture. Why three tiers?

**Category**: Architecture

**Answer**: The architecture separates concerns into Presentation (CloudFront + S3 + Route53), Application (ALB + ASG EC2), and Data (RDS MySQL) tiers. This separation provides independent scaling — the presentation tier scales via CloudFront edge caching globally, the application tier scales horizontally via Auto Scaling Group, and the data tier scales vertically with RDS instance class upgrades or read replicas. Each tier has its own security boundary enforced by dedicated security groups, enabling least-privilege network access. This pattern also allows teams to deploy and update each tier independently, reducing blast radius of changes.

---

## 2. Why did you choose a VPC with three subnet tiers instead of two?

**Category**: Networking

**Answer**: Two tiers (public + private) is common, but adding a third isolated data tier provides defense-in-depth. The private-data subnets have no route to the internet — not even via NAT Gateway. This means even if an attacker compromises an EC2 instance in the app tier, they cannot exfiltrate data from the database subnet to the internet directly. The only allowed path to the data tier is port 3306 from the app security group. This meets compliance requirements like SOC2 and HIPAA that mandate network isolation for data stores.

---

## 3. Explain your Security Group strategy and why you reference SG IDs instead of CIDRs.

**Category**: Security

**Answer**: The security groups form a chain: ALB SG (accepts 80/443 from internet) → App SG (accepts 8080 only from ALB SG) → RDS SG (accepts 3306 only from App SG). I reference security group IDs rather than CIDR blocks because SG references are dynamic — if IP addresses of instances change (which happens constantly with Auto Scaling), the rules still apply. CIDR-based rules would require manual updates. SG references also make the intent clear: "only the ALB can talk to app instances" vs. a list of IP ranges that may become stale.

---

## 4. Why use NAT Gateways instead of NAT Instances? What's the cost tradeoff?

**Category**: Cost / Architecture

**Answer**: NAT Gateways are AWS-managed, highly available within an AZ, and scale automatically to 45 Gbps. NAT Instances (EC2) require you to manage patching, scaling, and failover yourself. The tradeoff is cost: a NAT Gateway costs ~$32/month + $0.045/GB processed, while a t4g.nano NAT Instance costs ~$3/month. For dev environments, I use a single NAT Gateway to save costs (~$32/month vs. ~$97 for 3). For production, I deploy one NAT Gateway per AZ to eliminate cross-AZ data transfer charges and ensure AZ-independent egress.

## 5. How does Auto Scaling work in this architecture? What scaling policies did you choose?

**Category**: Scaling

**Answer**: I use two target tracking scaling policies: CPU utilization (target 70%) and ALB request count per target (target 1000 requests/instance). Target tracking is preferred over simple/step scaling because AWS automatically manages the CloudWatch alarms and scaling math. CPU-based scaling handles compute-intensive workloads, while request-count scaling handles I/O-bound workloads where CPU might stay low but response times degrade. The ASG uses rolling instance refresh with 50% minimum healthy percentage for zero-downtime deployments.

---

## 6. What happens if an Availability Zone goes down?

**Category**: Disaster Recovery

**Answer**: The architecture is designed for AZ failure resilience. The ALB is deployed across multiple AZs and automatically stops routing to unhealthy targets. ASG replaces terminated instances in surviving AZs (since we span 2-3 AZs). RDS Multi-AZ automatically fails over to the standby in a different AZ — typically within 60-120 seconds. NAT Gateways are per-AZ, so the surviving AZs maintain internet egress independently. CloudFront is globally distributed and unaffected by regional AZ failures.

---

## 7. Why did you use CloudFront OAC instead of OAI?

**Category**: Security

**Answer**: Origin Access Control (OAC) is the modern replacement for Origin Access Identity (OAI). OAC supports SSE-KMS encryption on S3 objects, supports S3 bucket policies with `AWS:SourceArn` conditions for tighter security, and works with all S3 features. OAI is a legacy approach that AWS recommends migrating away from. With OAC, the S3 bucket policy explicitly checks that the request comes from our specific CloudFront distribution ARN, preventing any other CloudFront distribution from accessing our bucket.

## 8. How do you handle database credentials without hardcoding them?

**Category**: Security

**Answer**: The RDS password is generated by Terraform's `random_password` resource and immediately stored in AWS Secrets Manager. The EC2 instances retrieve credentials at boot via the user_data script, which calls `aws secretsmanager get-secret-value` using the instance's IAM role — no passwords are ever in Terraform variables, `.tfvars` files, or application code. The IAM instance profile grants `secretsmanager:GetSecretValue` permission. In production, you'd add automatic secret rotation with a Lambda function on a 30-60 day schedule.

## 9. Why IMDSv2? What attack does it prevent?

**Category**: Security

**Answer**: IMDSv2 requires a session token obtained via a PUT request with a TTL header before metadata can be accessed. This prevents Server-Side Request Forgery (SSRF) attacks — like the Capital One breach — where an attacker tricks the application into making a GET request to `http://169.254.169.254/latest/meta-data/iam/security-credentials/` to steal IAM role credentials. With IMDSv2, the attacker can't easily forge the PUT request with the required hop limit of 1, because SSRF proxied requests add network hops.

## 10. Explain your Terraform state management strategy.

**Category**: CI/CD / Infrastructure

**Answer**: State is stored in S3 with versioning enabled and DynamoDB for state locking. S3 versioning allows rollback to previous state if an apply goes wrong. DynamoDB prevents concurrent modifications — if two engineers run `terraform apply` simultaneously, one will get a lock error. Each environment (dev/staging/prod) has its own state file with a distinct S3 key, preventing cross-environment state corruption. The state bucket has AES-256 encryption and public access blocked, since state files contain sensitive information like RDS endpoints and secret ARNs.

---

## 11. How would you implement blue/green deployments with this architecture?

**Category**: CI/CD

**Answer**: Create a second ASG with the new launch template (green), register it with a new target group, then modify the ALB listener to use weighted target groups — start with 90/10 blue/green split. Monitor error rates and latency via CloudWatch during the canary period. If healthy, shift to 0/100 and terminate the blue ASG. Alternatively, use AWS CodeDeploy with EC2 deployment groups for managed blue/green. For the data tier, schema migrations must be backward-compatible so both blue and green versions can query the same RDS instance during the transition.

## 12. What's the difference between your dev, staging, and prod configurations?

**Category**: Architecture / Cost

**Answer**: Dev uses single NAT Gateway, t3.micro instances (1 desired), single-AZ db.t4g.micro RDS with no Multi-AZ — optimized for cost (~$97/month). Staging mirrors production patterns: multi-AZ NAT, t3.small instances (2 desired), Multi-AZ db.t4g.small RDS. Production uses 3 AZs, c6i.large compute (3 desired, max 12), Multi-AZ db.r6g.xlarge RDS with 30-day backup retention and deletion protection enabled. Each environment has separate VPC CIDRs (10.0.0.0/16, 10.1.0.0/16, 10.2.0.0/16), separate state files, and separate AWS resources.

---

## 13. How do you handle SSL/TLS certificates across different services?

**Category**: Networking / Security

**Answer**: This is a common gotcha — CloudFront requires ACM certificates in `us-east-1` regardless of where your other resources are. I use a separate AWS provider aliased as `us_east_1` for the CloudFront certificate. The ALB uses a regional ACM certificate in the deployment region. Both certificates use DNS validation via Route53, which Terraform automates by creating the validation CNAME records. The certificates have `create_before_destroy` lifecycle rules to prevent downtime during renewal.

---

## 14. Your RDS has `skip_final_snapshot = true`. Is that production-safe?

**Category**: Disaster Recovery

**Answer**: No — in production, `skip_final_snapshot` should be `false` and `final_snapshot_identifier` should be set. I set it to `true` in the module defaults for ease of development and teardown. The production environment also has `deletion_protection = true`, which prevents accidental `terraform destroy` from deleting the database. Automated backups are retained for 30 days in production (7 in dev), and point-in-time recovery is enabled, providing RPO of 5 minutes.

---

## 15. How does your CI/CD pipeline prevent bad deployments?

**Category**: CI/CD

**Answer**: The GitHub Actions pipeline runs `terraform fmt -check` (style), `terraform validate` (syntax), and Checkov (security scanning) on every PR. The plan output is posted as a PR comment so reviewers can see exactly what will change. The `apply` job runs only on merge to main and requires the `production` environment approval gate — a human must click "Approve" in GitHub before apply runs. This prevents both accidental and unauthorized infrastructure changes.

## 16. What would you change if this needed to handle 10x traffic?

**Category**: Scaling

**Answer**: First, increase ASG max_size and adjust scaling thresholds. Second, add ElastiCache Redis between the app and data tiers to cache frequently-read queries and reduce RDS load. Third, add RDS read replicas and route read-heavy queries to them. Fourth, consider Aurora Serverless v2 which scales compute automatically. Fifth, move to CloudFront-heavy architecture by caching more API responses at the edge. Sixth, consider moving from EC2-based ASG to ECS Fargate or EKS for faster container-based scaling (seconds vs. minutes for EC2).

---

## 17. How do you monitor this infrastructure? What alerts would wake you up at 3 AM?

**Category**: Monitoring

**Answer**: CloudWatch monitors three critical metrics: ASG average CPU (alarm at >80% for 10 min), ALB target 5xx error count (alarm at >10 per minute), and RDS free storage space (alarm at <2GB). These fire to an SNS topic that sends email notifications. The CloudWatch dashboard provides a single-pane view of CPU, request count, response time, and database connections. For 3 AM pages, I'd prioritize: sustained 5xx errors (user-facing impact), RDS storage exhaustion (potential data loss), and ASG unable to scale (capacity crisis).

## 18. Why not use ECS/EKS instead of EC2 with ASG?

**Category**: Architecture Tradeoffs

**Answer**: EC2 + ASG was chosen because it demonstrates fundamental AWS networking and compute concepts clearly — ideal for a portfolio project. In a real enterprise migration path, I'd move to ECS Fargate for several reasons: faster scaling (no AMI boot time), simpler deployment (container image vs. user_data scripts), better resource utilization (no instance management), and built-in integration with ALB target groups. EKS would be appropriate if the organization needs Kubernetes ecosystem tools, multi-cloud portability, or complex service mesh requirements.

---

## 19. How does Terraform handle the circular dependency between CloudFront and S3 bucket policy?

**Category**: Infrastructure / Terraform

**Answer**: The S3 bucket policy needs the CloudFront distribution ARN (to restrict OAC access), but CloudFront needs the S3 bucket domain name as an origin. I handle this by creating the S3 bucket first, then CloudFront, then applying the bucket policy as a separate `aws_s3_bucket_policy` resource that depends on the CloudFront distribution. Terraform's dependency graph resolves this automatically. The `cloudfront_arn` variable in the S3 module is optional — if empty, the bucket policy isn't created, allowing the initial S3 creation to succeed.

## 20. If you had to redesign this for multi-region active-active, what would change?

**Category**: Architecture / Disaster Recovery

**Answer**: This is a significant architectural shift. Route53 would use latency-based routing to direct users to the nearest region. Each region would have its own VPC, ALB, ASG, and RDS infrastructure. RDS would use cross-region read replicas with promotion capability, or Aurora Global Database for sub-second replication. S3 would use cross-region replication for static assets. CloudFront would use origin groups with automatic failover between regional ALBs. The Terraform code would need a per-region module invocation pattern, and state would remain per-region to avoid blast radius. DynamoDB Global Tables could replace the state locking table for cross-region consistency. The cost roughly doubles, and operational complexity increases significantly.
